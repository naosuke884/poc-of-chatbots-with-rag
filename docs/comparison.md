# 2 方式の比較

ベクトル埋め込み方式と PageIndex 方式を、同じ 3 資料・同じ評価セット(148 問)・同じ回答生成(Claude Sonnet 5.5、同じプロンプト)で比べた結果。2 方式の違いは、回答生成に渡すコンテキストの集め方だけにしている。

評価セットは、人が作った 50 問(q01〜q50)に、LLM で作って点検した 98 問(q51〜q148、人は確認していない)を足したもの。作り方は README の「評価セット」を参照。

計測は 2026-10-24。問題ごとの結果(質問文・回答を含む)は `data/eval/results/` にあり、公開リポジトリのためコミットしていない。表は `uv run python -m rag_poc.compare` で出力したもの。

## 方式の構成

| | ベクトル | PageIndex |
|---|---|---|
| 索引 | ページをまたがない 600 文字前後のチャンク(150 文字重ね)、320 件 | 資料ごとの目次ツリー(節の見出し・ページ範囲・要約)、3 資料で 81 節 |
| 索引作成のモデル | OpenAI text-embedding-3-large(3072 次元) | Claude Haiku 5.5(PageIndex OSS 0.4.5) |
| 保存先 | PostgreSQL + pgvector | JSON ファイル |
| 検索 | 質問の埋め込みに近いチャンクを 8 件(追加検証として、チャンクのページ全体に広げる形と、資料ごとに 2 件ずつ足す形も計測) | 3 資料のツリーを Sonnet 5.5 に渡し、読むべき節を最大 5 つ選ばせる。そのページ本文を最大 10 ページ |
| 回答生成 | Claude Sonnet 5.5(共通) | Claude Sonnet 5.5(共通) |

- 料金は 1 問あたりの検索と回答生成の合計。採点の料金(2 回採点で 148 問あたり約 $2.7)は含まない

### LLM で作った問題について

- q51〜q148 の正答率は方式ごとに 95〜98% で、q01〜q50(94〜99%)と大きくは変わらなかった。言い回しを資料から離したが、正解ページの取得は 95〜96% で、50 問のときより落ちていない
- 4 方式とも外した q52(退職・契約終了時の対策)は、本編の問題として作ったが、付録 5 にも近い規程があり、各方式とも付録 5 にもとづいて答えた。質問が対象の資料を示しておらず、答えが 1 つに決まらない問題だった(点検で見落とした)。問題側の誤りと考えてよい
- PageIndex とページ拡張+資料枠で外した q75(取引先から高度な対策を求められた会社が目指す段階)は、正解(STEP3)は正しい。本編の表 2 は PDF から本文を取り出すと列の対応が崩れ、どの STEP の行かが本文だけでは読み取れない。表の前処理の課題(docs/report.md)

### ベクトル方式のページ拡張(追加検証)

ベクトル方式で取ったチャンクを、そのページの本文全体に置き換えてから回答生成に渡す形(表の「ベクトル(ページ拡張)」)も計測した。検索はベクトル方式と同じで、渡す本文だけが違う。計測は 2026-10-24。

- 正答率は 96% で、PageIndex 方式(97%)とほぼ並んだ。数値・表の問題は 100% になり、ベクトル方式で表の範囲を読み違えた問題も正解した
- 応答時間は平均 3.1 秒、1 問あたり $0.014 で、ベクトル方式から 0.3 秒・$0.003 増えただけ。PageIndex 方式の約半分の時間と約 6 割の料金
- 正解ページの取得はベクトル方式と同じ 91% なので、残る誤答 3 問はどれも正解ページを取得できていないもの(公開日・付録の案内)。これは検索の側の課題
- 148 問では 97%(ベクトル方式 95%)。ベクトル方式で不正解だった 5 問のうち 4 問が部分正解か正解になった

### 資料ごとの取得枠(追加検証)

ページ拡張に加えて、全体で近い 8 チャンクとは別に、資料ごとに近いチャンクを 2 件ずつ取り、まだ入っていないものを足す形(表の「ベクトル(ページ拡張+資料枠)」)も計測した。計測は 2026-10-24。

- きっかけ: ページ拡張でも落とした付録 3 の 3 問を調べると、正解のチャンクは付録 3 の中では 1 位だった。全体で並べると本編・付録 5 の似たチャンクに押され、2 位・9 位・18 位にとどまり、上位 8 件に入らないものがあった
- 正答率は 99%(49 / 1 / 0)で、付録 3 の問題は 3 問とも正解した(85% → 100%)。正解ページの取得は 96% で PageIndex 方式と並んだ
- 残る部分正解 1 問(公開日)は、正解のチャンクが本編の中でも 13 位で、資料ごとの枠では拾えない。質問と本文(改訂履歴の表)の言い回しが離れていることが原因
- 渡すページが増えるため、入力トークンは 1 問あたり約 8,400(ページ拡張は約 6,200)、料金は $0.018 になった。PageIndex 方式の約 3/4
- 応答時間は 2.8 秒で、ページ拡張(3.1 秒)より短かった。検索の時間はほぼ同じで、差は回答生成の時間の揺れ(計測した時間帯の違い)と考えられる。入力が増えたぶん速くなったわけではない
- 148 問(付録 3 の問題は 25 問)でも、正答率 98%・付録 3 の問題 100%・不正解 0 問で、4 方式で最も良かった。PageIndex 方式とは正答率で並び、応答時間は約半分(2.6 秒 対 5.1 秒)、料金は約 7 割($0.018 対 $0.026)
- 50 問では付録 3 の問題が 10 問しかなく、差は 3 問ぶんだった。資料が増えると 1 問あたりのチャンク数も資料数に比例して増えるため、資料が多い場合は枠の数か資料の絞り込み方を見直す

## 構築の手間

| | ベクトル | PageIndex |
|---|---|---|
| 索引作成の時間 | 4.9 秒(埋め込み) | 約 3.5 分(3 資料、LLM の呼び出し) |
| 索引作成の料金 | $0.021 | $0.036 |
| 用意するもの | ベクトル DB(pgvector)、チャンク分割の設計 | なし(ツリーは JSON で持てる) |
| コード量(索引作成 + 検索) | 約 170 行 | 約 190 行 |
| 決めること | チャンクの大きさ・重ね幅・取得件数 | 1 回に読むページ数の上限・選ぶ節の数 |
| 前処理 | 本編の余白の縦書き見出しの除去(共通) | 同左 |

- どちらも 1 日かからずに組めた。ベクトル方式は DB の準備があり、PageIndex 方式はツリーの中身(節の切れ目が本文と合っているか)の確認が要る
- PageIndex の索引作成は資料の構成に左右される。今回の 3 資料はどれも見出しがはっきりしていて、節の開始ページはすべて本文と合っていた。目次ページのない付録 3・付録 5 でも、本文から見出しを推定できた
- 資料を差し替えるとき、ベクトル方式は該当資料のチャンクを入れ替えるだけで済む。PageIndex 方式も資料ごとにツリーを作り直すだけだが、作成に数分かかる

## 誤答の傾向

この節は q01〜q50 で計測したときの分析。148 問で増えた誤答は、上の「LLM で作った問題について」と各追加検証の節に書いた。

### 両方式に共通

- 付録 3 の問題が最も弱い(ベクトル 75%、PageIndex 85%)。付録 3 の最終ページ(p8)は対策例のページで、対策ごとに活用する付録(付録 4・7・8 など)が書かれている。同じ付録の紹介は本編にもあるため、両方式とも本編の似た箇所を取得して付録 3 のページに届かなかった
- 「誰がいつ何をするか」をまとめる付録を問う問題は、両方式とも正解ページを取得できず「記載がない」と答えた。本編の案内にも付録の名前は出てくるが、質問と同じ言い回しではないため、回答生成が根拠として採らなかった
- 答えのない質問(6 問)は両方式とも全問「記載がない」と答えた。回答生成のプロンプトに「抜粋にない場合は答えない」と書いたのが効いている。そのぶん、上の問題のように答えがあるのに「記載がない」と答える側に倒れることがある

### ベクトル方式

- 外した 4 問のうち 3 問は、正解ページを検索で取得できていなかった(公開日・付録の案内など)。質問の言い回しと本文の言い回しが離れていると、近いチャンクに入ってこない
- 残る 1 問は、取得した表の範囲を読み違えた(Part 2・3 の項目番号)。この表は 1 ページで 4 つのチャンクに分かれており、取得したチャンクだけでは Part の境目が読み取れなかったことが一因と考えられる
- 数値・表の問題で 1 問落とした以外は、複数箇所にまたがる問題も含めて取得できている。8 チャンク(平均 5.6 ページ)で 3 資料から拾えている

### PageIndex 方式

- 外した 2 問はどちらも、付録 3 の問題で別の資料の節を選んだ。付録 3 のツリーは 8 ページで節が粗く、要約が英語で書かれた節もあったため、内容の近い付録 5・本編の節が選ばれた
- 正解ページを取得できた問題は、すべて正しく答えた。節単位でページを丸ごと渡すので、表や前後の文脈が切れない
- 1 問あたり平均 7 ページを読むため、入力トークンはベクトル方式の約 1.6 倍。加えて目次ツリー(約 2.7 万トークン)を毎回送る。プロンプトキャッシュで料金は 1 割に下がるが、ツリーは資料が増えるほど大きくなる
