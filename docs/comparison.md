# 3 方式の比較

シンプルなベクトル検索・ベクトル検索 + Jev で並べ替え・PageIndex の 3 方式を、同じ資料・同じ評価セット・同じ回答生成(Claude Sonnet 5.5、同じプロンプト)で比べた結果。方式の違いは、回答生成に渡すコンテキストの集め方だけにしている。本実装の第一候補は「ベクトル検索 + Jev で並べ替え」([採用方針](report.md))。

問題ごとの結果(質問文・回答を含む)は `data/eval/` にあり、公開リポジトリのためコミットしていない。表は `uv run python -m rag_poc.compare` と `uv run python -m rag_poc.retrieval_eval --table` で出力したもの。

## 方式の構成

| | ベクトル | ベクトル + Jev で並べ替え | PageIndex |
|---|---|---|---|
| 索引 | ページをまたがない 600 文字前後のチャンク(150 文字重ね)。3 冊で 320 件 | 同左 | 資料ごとの目次ツリー(節の見出し・ページ範囲・要約)。3 冊で 81 節 |
| 索引作成のモデル | OpenAI text-embedding-3-large(3072 次元) | 同左 | Claude Haiku 5.5(PageIndex OSS 0.4.5) |
| 保存先 | PostgreSQL + pgvector | 同左 | JSON ファイル |
| 検索 | 質問の埋め込みに近いチャンクを 8 件取り、それぞれのページ全体に広げる | 近いチャンクを 30 件取り、TypeSafe AI の Jev に「このチャンクに質問の答えが書かれているか」を判定させて上位 8 件を選び、それぞれのページ全体に広げる | 全資料のツリーを Sonnet 5.5 に渡し、読むべき節を最大 5 つ選ばせる。そのページ本文を最大 10 ページ |
| 回答生成 | Claude Sonnet 5.5(共通) | 同左 | 同左 |

- ベクトル系の 2 方式の違いは、並べ替えの有無だけ。取ったチャンクはどちらもページ全体に広げ(同じページは 1 つにまとめ、平均 6 ページ前後)、表や前後の文脈が切れないようにしている
- Jev は文章を書かず、yes/no などの判定を確率で返すモデル。1 回の呼び出しで 30 件のチャンクと 30 個の判定をまとめて送り、約 0.3 秒で返る
- 埋め込みは「話題が近いか」を測るので、言い回しが違うと答えのチャンクが上位に来ない。並べ替えは質問とチャンクを一緒に読ませて「答えが書かれているか」を判定するので、話題が近いだけのチャンクと見分けられる(公開日を問う q01 では、埋め込みで 14 位の正解チャンクが Jev で 1 位になった)

## 資料を 11 冊に増やしたとき(検索だけ)

3 冊・148 問では正答率が 95〜100% に集まり差が出にくかったため、似た記述の多い資料を足して検索の精度を比べた。足したのは同じガイドラインの付録・説明資料のうち PDF で配布されている 8 冊(付録 1・7・8、自社診断 解説編、6 か条 解説編、説明資料 3 冊)で、合計 388 ページ。回答生成と採点はせず、検索だけを流して正解ページを取得できたかを測った(`rag_poc.retrieval_eval`)。計測は 2026-10-31、方式ごとに単独で走らせた。

| ベクトル | 93% → 92% | 85% → 98% | 91% | 5.8 → 6.4 | 0.2 → 0.2 秒 | $0.00001 → $0.00001 |
| ベクトル + Jev で並べ替え | 100% → 98% | 100% → 100% | 97% | 5.8 → 6.2 | 0.5 → 0.4 秒 | $0.00065 → $0.00060 |
| PageIndex | 97% → 97% | 85% → 98% | 96% | 7.8 → 8.7 | 2.7 → 2.9 秒 | $0.00753 → $0.01853 |

- 「追加資料の問題」は、追加の 8 冊から作った 95 問(`rag_poc.evalgen_extra`。102 問を下書きし、11 冊の全文と照らした点検を 95 問が通過、人は確認していない)。それ以外の列は元の 148 問
- 正解ページは、ほかの資料に同じ答えがあるページも正解として数えた(`rag_poc.evalgold`。Opus 5.5 に、そのページだけで正解の要点がわかるページを挙げさせた)。元の 148 問のうち 42 問、追加資料の 95 問のうち 47 問に、ほかの資料にも正解のページがあった
- 元の 148 問では、資料を 2.8 倍に増やしても正解ページの取得はほとんど下がらなかった。元の正解ページだけで数えるとベクトル 93% → 86%、PageIndex 97% → 93% と下がるが、追加の資料の同じ内容のページを取るようになっただけ
- 追加資料の問題では方式の差が開いた。ベクトル 91%、PageIndex 96%、Jev で並べ替え 97%。元の正解ページだけで数えるとベクトル 85%、PageIndex 88%、Jev で並べ替え 97% で、並べ替える方式は問題を作ったページそのものを取れている
- ベクトルで落とした問題は自社診断 解説編(110 ページ)と付録 8 に多く、取ったページは同じ資料の別のページや、内容の近い資料のページに分かれていた
- PageIndex は目次ツリーが約 3 倍(7.9 万トークン)になり、検索の料金が 2.5 倍になった。ほかの 2 方式はほとんど変わらない

自前の評価セットは LLM で作った問題が多く人が確認していないため、公開の日本語 RAG ベンチマーク [Allganize RAG-Evaluation-Dataset-JA](https://huggingface.co/datasets/allganize/RAG-Evaluation-Dataset-JA)(MIT ライセンス)でも計測した。官公庁・業界団体などが公開している PDF を 5 業種(金融・情報通信・製造・公共・流通小売)で集め、業種ごとに 60 問の質問と正解(正解のページ番号付き)を人が作ったもの。計測は 2026-10-31、15 本(5 業種 × 3 方式)を同時に走らせた(`rag_poc.allganize` で変換、`RAG_CORPUS=ag_<業種>`、表は `uv run python -m rag_poc.compare --ag`)。

### 図・画像の中身を文字に起こす前処理(追加検証)

## 誤答の傾向(3 冊・148 問)

### ベクトル

- 不正解 1 問・部分正解 8 問。多くは正解ページを取得できていないもの(公開日、付録 3 の対策例のページ、本編の脚注にある委員会の性格など)。質問と本文の言い回しが離れていると、近いチャンクの上位 8 件に入らない
- 付録 3 の問題が最も弱い(92%)。付録 3 の正解チャンクは付録 3 の中では 1 位でも、全体で並べると本編・付録 5 の似たチャンクに押されて漏れる
- 正解ページを取得できた問題はほとんど正しく答えた。部分正解のうち 2 問(q100・q113)は、正解ページを取りながら回答が要点の一部を誤ったもの

### ベクトル + Jev で並べ替え

- 部分正解 1 問(q113)だけ。正解の 2 ページのうち 1 ページが漏れ、回答が注記を見落とした
- ほかの方式で落とした公開日(q01)・付録 3(q47・q48)・段組みの表(q75)なども正解した。q75 は 1 回の計測でのことで、表の取り出しの課題(report.md)が解けたわけではない
- 並べ替えの上限は、埋め込みで取った 30 件の候補に正解が入っているか。11 冊で、正解ページが 30 件の候補に入っていた割合は 98% だった

### PageIndex

- 不正解 2 問・部分正解 2 問。q75 は本編の表 2 が PDF から取り出すと列の対応が崩れ、どの STEP の例かを本文から読み取れなかった。q63 は付録 5 のログの保存期間の規定のページを取り、ログが自動削除されるという本編の記述のページを取らなかった
- 正解ページを取得できた問題は、ほとんど正しく答えた。節単位でページを丸ごと渡すので、表や前後の文脈が切れない
- 目次ツリー(3 冊で約 2.7 万トークン)を毎回送る。プロンプトキャッシュで料金は 1 割に下がるが、ツリーは資料が増えるほど大きくなる

### 共通

- 答えのない質問(21 問)は 3 方式とも全問「記載がない」と答えた。回答生成のプロンプトに「抜粋にない場合は答えない」と書いたのが効いている。そのぶん、答えがあるのに「記載がない」と答える側に倒れることがある
- q52(退職・契約終了時の対策)は本編の問題として作ったが、付録 5 にも近い規程があり、ベクトルと PageIndex は付録 5 にもとづいて答えた。問題の作り方の課題(対象の資料を質問に含めていない)
