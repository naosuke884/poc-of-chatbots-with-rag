# 採用方針と本実装に向けた課題

[2 方式の比較](comparison.md)をもとにした、本実装の方式の提案と、本実装の前に解いておく課題・追加で確かめること。

## 結果の要約

- 精度は PageIndex 方式がやや良い(正答率 97% 対 94%、正解ページの取得 96% 対 91%)。ただし差は 50 問中 1〜2 問ぶん
- 速度と料金はベクトル方式が良い。応答時間は半分(2.8 秒 対 5.8 秒)、1 問あたりの料金は半分以下($0.011 対 $0.024)
- 構築の手間はどちらも小さい。索引作成はどちらも数セント
- 両方式とも同じ問題を落としている。弱点は検索方式よりも、資料間で似た記述があるときにどの資料のページを取るか、にある

## 採用方針(提案)

**ベクトル方式を基本にし、取得したチャンクを「そのページ全体」に広げてから回答生成に渡す形を本実装の第一候補にする。**

- 理由 1: 精度の差は小さく、速度と料金の差ははっきりしている。チャットで 1 問ごとに待つ時間が 3 秒か 6 秒かは体感で効く
- 理由 2: 資料が増えたときの伸び方が違う。PageIndex 方式は全資料の目次ツリー(今は約 2.7 万トークン)を毎回送るので、資料数に比例して検索の時間と料金が増える。ベクトル方式は件数が増えても検索時間はほぼ変わらない
- 理由 3: PageIndex 方式が良かった点(正解ページを取れれば表や前後の文脈が切れない)は、チャンクをページ単位に広げればベクトル方式でも取り込める。今回のベクトル方式の誤答のうち 1 問(表の項目番号の読み違い)は、表が 4 つのチャンクに分かれていたことが一因と考えられる
- PageIndex 方式を採るのがよい場合: 対象が数冊の構造化された文書に限られ、応答時間より精度を優先するとき。この場合は今回の実装をほぼそのまま使える

この提案は今回の 3 資料・50 問での結果にもとづく。追加検証 1 で「ページ全体に広げる」形を計測し、正答率 96%(PageIndex 方式 97%)・応答時間 3.1 秒・1 問あたり $0.014 となった。精度はほぼ PageIndex 方式に並び、速度と料金はベクトル方式に近いので、提案どおりこの形を第一候補とする。

## 本実装の前に確かめること(追加検証)

1. **ベクトル方式でページ全体に広げる形の計測**(済み): 取得チャンクのページ本文を渡す形で、同じ評価セットを計測した。精度が PageIndex 方式とほぼ並び、応答時間と料金はベクトル方式に近かった([比較](comparison.md#ベクトル方式のページ拡張追加検証))
2. **資料の絞り込み**: 両方式とも、本編に似た記述がある付録 3 の問題を落とした。質問から対象の資料を先に絞る、または資料名をチャンクに含めて検索する形を試す
3. **資料数を増やしたときの伸び方**: 本実装で扱う資料の量(冊数・ページ数)で、PageIndex 方式のツリーの大きさと応答時間、ベクトル方式の検索時間を測る
4. **評価セットの拡充**: 50 問では 1〜2 問の差しか測れない。本実装の対象資料で、利用者が実際にしそうな質問を 100〜200 問に増やす。言い回しを資料と変えた質問(今回の誤答の主因)を意識して入れる
5. **採点の信頼性**(済み): 最初の計測で、正しい回答を部分正解とした採点の誤りが 1 問あった。採点に正解の根拠ページの本文を渡し、2 回採点して食い違った問題を人が見る手順にした。採点し直すと誤りは直り、食い違った問題はなかった

## 本実装に向けた課題

### 資料の前処理

- PDF のテキスト抽出で、余白の縦書き見出しのような本文以外の文字が混ざる。資料ごとに除き方を決める必要がある(今回は本編だけ、位置で除いた)
- Word で配布される資料(付録 5)は PDF に変換して扱った。ページ番号を根拠として示すなら、配布物と同じページになる変換方法を決める
- 資料の改訂時に索引を作り直す手順(どの資料を、いつ、誰が)を決める

### 検索と回答

- 答えのない質問には全問「記載がない」と答えられたが、その分、答えがあるのに「記載がない」と答える誤りが両方式で出た。言い回しが違うだけの質問をどこまで拾うかは、プロンプトと検索件数の調整が要る
- 回答の根拠ページは LLM が挙げたものを表示している。画面で根拠のページを開けるようにするなら、ページ番号と配布物のページの対応を保証する
- 応答時間の大半は回答生成(約 2.6〜2.9 秒)。体感を良くするには、回答をストリーミングで表示する
- 回答モデルが回答を拒否した場合、今は結果に残すだけにしている。本実装では別モデルへの切り替え(fallbacks)を入れるか決める

### PageIndex 方式を採る場合

- 節の要約が英語で書かれることがある。索引作成のプロンプトで要約の言語を指定する
- 目次ページのない資料では、節の切れ目を PageIndex が本文から推定する。資料ごとに節の開始ページが合っているかを確かめる手順が要る

### ベクトル方式を採る場合

- text-embedding-3-large は 3072 次元で、pgvector の vector 型では索引を張れない(2000 次元まで)。今回は 320 件なので全件走査にしたが、件数が増えたら halfvec 型で HNSW 索引を張る
- チャンクの大きさ・重ね幅・取得件数は今回決め打ちにした。追加検証 1 とあわせて調整する

### 運用

- 1 問あたりの料金は $0.01〜0.03 で、PoC 全体でも API 利用料は $3 程度だった。本実装では利用量の上限と、利用状況を確認する仕組みを用意する
- 今回は対象外にしたマルチターン会話と認証は、本実装の要件として改めて決める
