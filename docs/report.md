# 採用方針と本実装に向けた課題

[3 方式の比較](comparison.md)をもとにした、本実装の方式の提案と、本実装の前に解いておく課題。

## 結果の要約

| | ベクトル | ベクトル + Jev で並べ替え | PageIndex |
|---|---|---|---|
| 正答率(3 冊・148 問) | 97% | **100%** | 98% |
| 正解ページの取得(3 冊・148 問) | 93% | **100%** | 97% |
| 正解ページの取得(11 冊・148 問) | 92% | **98%** | 97% |
| 正解ページの取得(11 冊・追加資料の 95 問) | 91% | **97%** | 96% |
| 応答時間(3 冊) | **2.6 秒** | 3.2 秒 | 5.1 秒 |
| 1 問あたりの料金(3 冊) | **$0.014** | $0.015 | $0.026 |
| 資料が増えたとき | 時間・料金ともほぼ一定 | 時間・料金ともほぼ一定 | 検索の時間と料金が資料数に比例して増える |

- 精度は「ベクトル + Jev で並べ替え」が最も良く、PageIndex がそれに次ぐ。シンプルなベクトル検索は、似た記述が他の資料にあると正解のページを取り逃がす
- ベクトル系の 2 方式は、どちらも取ったチャンクをページ全体に広げて渡し、違いは並べ替えの有無だけ。並べ替えの分は 0.3 秒・1 問 $0.0007 ほどしか増えない
- 速さと料金はベクトル系が良い。PageIndex の約 6 割の時間と料金で済む
- 似た記述の多い資料を足して 11 冊にすると、3 方式の差が開いた(追加資料の問題でベクトル 91% に対して並べ替え 97%)
- 精度の向上は並べ替えそのものによる。同じ並べ替えを Claude Haiku 5.5 で行っても精度は同じだった(並べ替えに約 4 秒かかる)

## 採用方針(提案)

**ベクトル検索で近いチャンクを 30 件取り、Jev で「答えが書かれているか」を判定して上位 8 件を選び、それぞれのページ全体に広げてから回答生成に渡す形を本実装の第一候補にする。**

```
質問
 │ ① 埋め込み(text-embedding-3-large)で近いチャンクを 30 件      約 0.2 秒
 │ ② 30 件を Jev に 1 回で渡し、答えが書かれている確率の高い 8 件   約 0.3 秒
 │ ③ 8 件をそれぞれのページ全体に広げる(平均 6 ページ)
 ▼
 ④ Claude Sonnet 5.5 が、渡したページだけを根拠に回答する          約 2.7 秒
```

- 理由 1: 3 方式で精度が最も良い。埋め込みは話題の近さしか測れないが、並べ替えで答えそのものが書かれたチャンクを上位に出せる。ページ全体に広げるので、表や前後の文脈も切れない
- 理由 2: 速さと料金がシンプルなベクトル検索に近い。PageIndex の約 6 割の時間と料金で済む
- 理由 3: 資料が増えても、候補は 30 件・渡すのは最大 8 ページのままで、時間と料金がほぼ変わらない。PageIndex は目次ツリーを毎回送るので、11 冊で 1 問あたりの節の選択が $0.019・2.9 秒、44 冊で $0.065・5.5 秒と資料数に比例して増える
- 理由 4: 索引作りは埋め込みだけで、1,000 ページあたり約 $0.1・数秒。PageIndex のツリー作成(1 冊あたり数十秒〜数分)が要らない

### 状況に応じた代わりの構成

| 状況 | 構成 | 違い |
|---|---|---|
| Jev を使えない(契約・データの取り扱い・提供の安定性) | ② を Haiku 5.5 での並べ替えにする | 精度はほぼ同じ。並べ替えに約 4 秒かかり、応答時間は 7 秒前後 |
| 精度を最優先する | ① ② の結果に PageIndex で選んだページを足し、Jev でもう一度絞る | 11 冊で正解ページの取得 99%(試算)。検索に約 3 秒かかり、料金は資料数に比例して増える |
| 対象が数冊の構造化された文書で、外部の判定モデルを使いたくない | PageIndex | 精度は並べ替えに次ぐ。今回の実装をほぼそのまま使える |

## 本実装の前に確かめること

- **Jev の利用条件**: Jev は 2026-09 公開の早期アクセスのサービスで、資料の本文を外部に送る。契約・データの取り扱い・提供の安定性・正式な料金を確かめる。料金は紹介記事の単価($0.042 / 100 万トークン)で見積もっており、公開の料金表は見つかっていない
- **並べ替えの上限**: 正解が埋め込みの上位 30 件に入っていなければ、並べ替えでも取れない。11 冊で、正解ページが 30 件の候補に入っていた割合は 98%。本実装の資料の量で、候補の件数を確かめる(Jev は 1 回に渡せる量に上限があり、約 3.4 万トークンまでは通った)
- **本実装の資料での評価**: 評価セットの多くは LLM が作って点検した問題で、人は確認していない。採点も LLM。各方式の計測は 1 回ずつで、1〜2 問ぶんの揺れがある。本実装の対象資料で評価セットを作り直し、人が確認する

## 検証の経緯

1. **2 方式の比較**(3 冊・50 問): シンプルなベクトル検索は正答率 94%・2.8 秒・$0.011、PageIndex は 97%・5.8 秒・$0.024。精度の差は小さく、速さと料金の差がはっきりしていた
2. **ベクトル検索の改良**: 取ったチャンクをページ全体に広げる形(96%)、資料ごとに上位 2 件を足す形(99%)を試した。ページ全体に広げる形は、表や前後の文脈が切れないので、ベクトル系の基準にした。資料ごとの枠は精度が上がるが、資料数に比例して渡すページが増えるため採らなかった
3. **採点の信頼性**: 正しい回答を部分正解とした採点の誤りが 1 問あった。採点に正解の根拠ページの本文を渡し、2 回採点して食い違った問題を人が見る手順にした
4. **評価セットの拡充**: LLM で 98 問を作って点検し、148 問にした。方式の順位は変わらなかった
5. **Jev での並べ替え**: 30 件の候補を Jev で並べ替える形が正答率 100%・3.2 秒・$0.015 で最も良かった。同じ並べ替えを Haiku で行っても精度は同じで、精度の向上は並べ替えそのものによる
6. **資料を増やしたときの伸び方**: 11 冊と、それを複製した最大 352 冊で時間と料金を測った([下記](#資料を増やしたときの伸び方))
7. **11 冊での検索の精度**: 似た記述の多い 8 冊を足し、追加の資料から作った 95 問も加えて検索だけを測った。並べ替える方式と PageIndex の差、シンプルなベクトル検索との差が開いた
8. **PageIndex との組み合わせ**: 節の選択を Jev で行う形(83〜88%)、ベクトルで資料を絞ってから PageIndex + Jev の形(89%)を試したが、どちらも精度が下がった。目次探索には LLM の推論が要り、資料を先に絞ると絞り込みで正解の資料が漏れる

採らなかった方式の結果は [比較](comparison.md#試して採らなかった方式) にまとめた。

## 資料を増やしたときの伸び方

計測は 2026-10-24、`uv run python -m rag_poc.scale` で測り、結果は `data/index/scale.json` にある。22 冊以上は 11 冊を複製した合成で、中身が同じなので精度は測らず、時間と料金だけを見た。

### 索引作成

|---|---|---|
| 追加 8 冊(248 ページ)の時間 | 3.6 秒(埋め込み 302 チャンク) | 約 9 分(1 冊 40〜105 秒、冊数に比例) |
| 追加 8 冊の料金 | $0.013 | $0.060 |
| 1,000 ページあたりの料金(目安) | 約 $0.05〜0.15(本文の量による) | 約 $0.25 |

### 1 問あたりの検索

| 資料数(ページ数) | 3(140) | 11(388) | 22(776) | 44(1,552) | 88(3,104) | 352(12,416) |
|---|---|---|---|---|---|---|
| ベクトル系: チャンク数 | 320 | 622 | 1,244 | 2,488 | 4,976 | 19,904 |
| ベクトル系: DB の検索(上位 8 件) | 1 ms | 2 ms | 4 ms | 9 ms | 18 ms | 77 ms |
| PageIndex: 節の数 / ツリーのトークン | 81 / 2.7 万 | 262 / 7.9 万 | 524 / 15.7 万 | 1,048 / 31.4 万 | - | - |
| PageIndex: 節の選択の時間(キャッシュあり) | 2.5 秒 | 3.3 秒 | 4.3 秒 | 5.5 秒 | - | - |
| PageIndex: 節の選択の料金(キャッシュあり / キャッシュ作成時) | $0.007 / $0.055 | $0.017 / $0.16 | $0.033 / $0.32 | $0.065 / $0.63 | - | - |

- ベクトル系の検索時間の大半は質問の埋め込み(資料の量によらず平均 0.14 秒)で、DB の検索は 2 万チャンクでも 0.08 秒。これ以上の規模では halfvec 型で HNSW 索引を張る

## 本実装に向けた課題

### 資料の前処理

- PDF のテキスト抽出で、余白の縦書き見出しのような本文以外の文字が混ざる。資料ごとに除き方を決める必要がある(今回は本編だけ、位置で除いた)
- 段組みの表は、PDF から本文を取り出すと行と列の対応が崩れる。本編の表 2(STEP ごとの想定企業の例)では、どの STEP の例かが本文から読み取れず誤答が出た。表の多い資料は、表を行ごとの文に直す、またはページ画像を回答生成に渡すかを決める
- Word で配布される資料(付録 5)は PDF に変換して扱った。ページ番号を根拠として示すなら、配布物と同じページになる変換方法を決める
- 資料の改訂時に索引を作り直す手順(どの資料を、いつ、誰が)を決める

### 検索と回答

- text-embedding-3-large は 3072 次元で、pgvector の vector 型では索引を張れない(2000 次元まで)。今回は数百件なので全件走査にしたが、件数が増えたら halfvec 型で HNSW 索引を張る
- チャンクの大きさ・重ね幅・候補数(30 件)・渡す件数(8 件)は今回決め打ちにした。本実装の資料で調整する
- 答えのない質問には全問「記載がない」と答えられたが、その分、答えがあるのに「記載がない」と答える誤りも出る。プロンプトと候補数で調整する
- 回答の根拠ページは LLM が挙げたものを表示している。画面で根拠のページを開けるようにするなら、ページ番号と配布物のページの対応を保証する
- 応答時間の大半は回答生成(約 2.5 秒)。体感を良くするには、回答をストリーミングで表示する
- 回答モデルが回答を拒否した場合、今は結果に残すだけにしている。本実装では別モデルへの切り替え(fallbacks)を入れるか決める
- Jev が使えない・遅いときに、並べ替えなしのベクトル検索に切り替えるかを決める

### 運用

- 1 問あたりの料金は $0.014〜0.026 で、PoC 全体の API 利用料は約 $75 だった(大半は評価セットの作成と採点)。本実装では利用量の上限と、利用状況を確認する仕組みを用意する
- 今回は対象外にしたマルチターン会話と認証は、本実装の要件として改めて決める
